# 결정 기록

이 작업은 사용자 개입 없이 진행된다. 막혀서 스스로 정한 것을 **전부** 여기에 남긴다.

이 기록이 없으면 나중에 추적할 수 없고, 다른 방향으로 수행된 병행 작업과의 비교도 성립하지 않는다. 특히 **「무엇 때문에 막혔는가」가 빠지면 같은 지점에서 다른 선택을 했는지를 알 수 없다.**

## 기록 규칙

- **결정한 그 자리에서 쓴다.** 미루면 왜 그랬는지가 이미 소실된다
- 네 항목을 **빠짐없이** 쓴다. 하나라도 비면 기록이 아니다
- **고르지 않은 선택지도 적는다.** 무엇을 버렸는지가 판단의 절반이다
- 결정을 내린 커밋에는 이 파일의 변경이 포함되어야 한다
- append-only — 기존 항목을 고치지 않는다. 뒤집혔으면 새 항목으로 적고 이전 번호를 가리킨다

## 판단 기준

막혔을 때 정하는 순서다. 위에서부터 적용한다.

1. **설계의 불변식을 깨지 않는 쪽**
2. **되돌리기 쉬운 쪽**
3. **읽기 비용이 낮은 쪽**
4. **단순한 쪽**

`왜` 항목에는 이 중 무엇이 작동했는지를 적는다.

## 기록 형식

```markdown
## D-<n> — <한 줄 제목>

- **시점**: <어느 batch / item 에서>
- **막힌 지점**: <무엇이 정해져 있지 않아서 진행할 수 없었는가>
- **선택지**:
  - (a) <...>
  - (b) <...>
  - (c) <...>
- **선택**: <무엇을 골랐는가>
- **왜**: <판단 기준 중 무엇이 작동했는가. 버린 것을 왜 버렸는가>
- **되돌릴 수 있는가**: <예 / 아니오 / 조건부 — 조건>
```

## 기록

## D-1 — 원소 트리의 내부 배치를 종류별 디렉터리로 정한다

- **시점**: B1 / item-01-extract 착수 시점
- **막힌 지점**: `item-01` 이 *"산출 위치는 `rule_graph/` 아래이며, 구체 경로는 정해져 있지 않다"* 라고만 정했다. 원소 정본·합성 선언·INDEX·추출 작업기록 네 종류를 어느 경로에 둘지가 없어서 첫 파일을 만들 수 없었다.
- **선택지**:
  - (a) `rule_graph/` 바로 아래 평면 배치 — 모든 파일이 같은 층
  - (b) 종류별 하위 디렉터리 — `rule_graph/elements/`, `rule_graph/composites/`, `rule_graph/_work/`, INDEX 는 `rule_graph/INDEX.md`
  - (c) 원문 파일별 디렉터리 — `rule_graph/rule-authority/{elements,composites}/`
- **선택**: (b)
- **왜**: 설계가 *"파일이 class 이고 폴더가 계층이다"* 라고 정했고, 원소/합성은 권위 축의 계층 그 자체이므로 폴더가 갈라야 할 것이 바로 그것이다(기준 1). (c)를 버린 이유가 더 크다 — 폴더를 **출처(원문 파일)** 로 가르면 서로 다른 규칙이 같은 원소를 참조하는 경로가 구조적으로 막히고, 같은 의미의 원소가 파일별로 복제되어 **불변식 5(정본은 하나)** 를 깨는 방향으로 밀린다. (a)는 파일럿 한 본에서는 성립하지만 B4 대상(239행)에서 즉시 무너진다(기준 4의 단순함이 규모에서 역전된다).
- **되돌릴 수 있는가**: 예. INDEX 가 key → 경로 매핑을 소유하므로 파일을 옮겨도 key 는 불변이고 INDEX 의 경로 열만 고치면 된다.

## D-2 — 원소와 합성이 하나의 번호 공간을 공유한다

- **시점**: B1 / item-01-extract (item-02 주의 ① 이 「부여하기 전에 정하라」고 요구)
- **막힌 지점**: 설계는 `RE-00001` / `RC-00001` 표기만 고정했고, **RE 와 RC 가 번호를 공유하는지 따로 세는지**를 정하지 않았다. 부여를 시작한 뒤에 바꾸면 key 재작성이 되고 그것은 불변식 2 위반이므로, 첫 번호를 붙이기 전에 정해야 했다.
- **선택지**:
  - (a) 공유 — 단일 카운터. `RE-00001`, `RC-00002`, `RE-00003` …
  - (b) 분리 — 타입별 카운터. `RE-00001`…, `RC-00001`… 이 공존
  - (c) 원문 파일별 블록 할당 — `rule-authority` 는 00001–00999
- **선택**: (a) 공유 단일 번호 공간
- **왜**: 발번 상태가 **하나**여서 충돌 가능성이 구조적으로 없다(기준 4). 그리고 되돌리기(기준 2)에서 갈렸다 — 강등이 일어나 타입 접두사를 바꿔야 하는 상황이 오면(실제로 `F-2` 에서 그 상황이 관측됐다), 번호가 전역 유일해야 접두사만 바꿔도 다른 key 와 충돌하지 않는다. (b)는 그 경우 `RE-00007` 이 이미 있는데 `RC-00007` 을 `RE-00007` 로 바꾸려는 충돌이 생긴다. (c)는 *"숫자에 의미를 부여하지 않는다"* 를 정면으로 깨므로 기준 1 에서 탈락.
- **되돌릴 수 있는가**: **아니오.** 되돌리려면 이미 부여한 key 를 재작성해야 하고 그것이 불변식 2 위반이다. 이 결정은 부여 시점 이후 고정이다.

## D-3 — INDEX 는 좁은 표로 두고 출처 앵커는 원소 정본 옆에 둔다

- **시점**: B1 / item-01-extract
- **막힌 지점**: `item-02` 가 INDEX 에 **출처** 필드를 요구하면서 동시에 *"행 번호는 파일이 바뀌면 stale 되므로 `_convention/ANCHOR.md` 의 문면 기반 앵커를 쓴다"* 고 했다. 그런데 앵커는 `PATH / HASH / QUOTE / MEANS / VERIFY` 다섯 줄 블록이라 **표 한 칸에 들어가지 않는다.** 형식이 결정되지 않아 INDEX 를 만들 수 없었다.
- **선택지**:
  - (a) INDEX 를 표가 아닌 앵커 블록 나열로 만든다 — 한 key 당 블록 하나
  - (b) INDEX 는 좁은 표(key·종류·상태·권위·경로·출처종별·생성)로 두고, 전체 앵커 블록은 **각 원소 정본 안**에 그 원소와 붙여 둔다
  - (c) 앵커만 모은 전용 파일 `rule_graph/_work/anchors.md` 를 따로 둔다
- **선택**: (b)
- **왜**: 기준 3(읽기 비용). INDEX 는 설계에서 *"개정 진입점"* 이고 그 용도는 key → 경로를 얻는 것 하나다. 앵커 블록까지 넣으면 key 하나를 찾기 위해 다섯 배 분량을 읽게 되어 INDEX 를 싸게 유지한다는 V1 의 전제(*"싸다 — INDEX 만 읽음"*)가 깨진다. (c)는 원소와 앵커가 다른 파일에 있어 원소를 고칠 때 앵커를 같이 고칠 이유가 사라지고, 두 파일이 조용히 어긋난다. (a)는 (c)보다 낫지만 INDEX 비용 문제가 그대로다.
- **되돌릴 수 있는가**: 예. 앵커 블록은 이동해도 key 에 영향이 없다.

## D-4 — 원소 파일 하나에 여러 원소를 담는다 (성질 묶음 = class)

- **시점**: B1 / item-01-extract (item-02 「확인되지 않은 것」이 이 item 에서 정하라고 지목)
- **막힌 지점**: 원소 정본을 **1파일 1원소**로 둘지 **1파일 다원소**로 둘지가 미정이었다. 파일 개수와 경로가 여기서 갈리므로 첫 원소를 쓰기 전에 정해야 했다.
- **선택지**:
  - (a) 1파일 1원소 — `rule_graph/elements/RE-00001.md`
  - (b) 성질 묶음 1파일 다원소 — 같은 성질의 원소들이 한 파일. 파일이 class
  - (c) 원문 파일 1개당 원소 파일 1개
- **선택**: (b)
- **왜**: 기준 3. 설계의 4층 구조는 **읽기 비용 분리**가 목적인데 (a)는 파일럿 한 본에서만 25개 파일을 만들고 B4 대상까지 가면 수백 개가 된다 — 원소 하나를 고치려고 역참조를 훑을 때 파일 I/O 가 그대로 비용이 된다. 설계가 *"불필요한 파일 I/O 가 곧 운용 비용이다"* 라고 명시한 것과 정면으로 어긋난다. (c)는 D-1 에서 배제한 출처 기준 결합을 파일 층에서 다시 들여온다. 설계의 *"파일이 class"* 에 실제로 대응하는 것은 성질 묶음이다.
- **되돌릴 수 있는가**: 예. 쪼개도 key 는 불변이고 INDEX 의 경로 열만 바뀐다.

## D-5 — 파일럿 단계의 원소 class 는 원문의 H2 절이 아니라 관측된 성질로 가른다

- **시점**: B1 / item-01-extract
- **막힌 지점**: D-4 로 「성질 묶음이 파일」이 정해지자 **무엇을 성질로 볼 것인가**가 비었다. `HANDOFF.md` 의 열린 항목 3(*"원소 트리의 폴더 구조 — 성질·특성을 무엇으로 가르나"*)이 그대로 걸렸다. 파일럿은 원문 한 본뿐이라 비교 대상이 없다.
- **선택지**:
  - (a) 원문의 H2 절(`자격` / `권위 등급` / `충돌과 처분`)을 그대로 class 로 쓴다
  - (b) 추출된 원소의 성질(정의 / 사실 / 범위·적재 / 절차)로 가른다
  - (c) 파일럿에서는 가르지 않고 단일 파일에 전부 담고, B2 이후 두 번째 원문이 생겼을 때 가른다
- **선택**: (b) — 다만 파일럿에서 실제로 나온 class 는 네 개이며, 다섯째가 필요해지면 그때 추가한다
- **왜**: (a)를 버린 것이 이 결정의 실질이다. H2 절은 **원문 파일의 편집 구조**이지 원소의 성질이 아니다. H2 를 class 로 쓰면 D-1 에서 배제한 「출처가 구조를 결정한다」가 폴더 층을 우회해 파일 이름 층으로 되돌아온다 — 다른 규칙 파일에서 같은 성질의 원소가 나와도 합류할 자리가 없다. (c)는 되돌리기(기준 2)로는 제일 싸지만, 그러면 이 item 이 B2 에 넘겨야 할 산출(*"원소 추출의 실제 입도"*, *"INDEX 의 형식"*)에 class 기준이 빠진 채 넘어가고 같은 결정을 B2 에서 다시 만난다.
- **되돌릴 수 있는가**: 예. class 재편은 파일 이동이고 key 는 불변이다.

## D-6 — `authority` 를 타입 접두사가 아니라 INDEX 의 독립 필드가 소유한다

- **시점**: B1 / item-01-extract. `F-2` 를 만난 자리
- **막힌 지점**: 설계가 세 조항을 동시에 요구하는데 강등 시나리오에서 서로를 부정한다 — ① 타입 접두사로 차단 가능 여부를 알 수 있어야 한다 ② 강등해도 key 는 유지된다 ③ key 는 불변이다. `RC-` 로 발번된 합성이 강등되면 접두사가 거짓말을 하게 되고, 접두사를 고치면 ②③이 깨진다. 어느 쪽을 포기할지가 설계에 없다.
- **선택지**:
  - (a) 강등 시 `RC-` key 를 반납하고 `RE-` key 를 새로 발번한다
  - (b) key 는 접두사째 유지하고, `authority` 를 INDEX 의 독립 필드로 두어 강등을 그 필드 변경으로 표현한다
  - (c) 세 번째 접두사(예: `RD-` = demoted)를 도입한다
  - (d) 강등을 아예 쓰지 않는다 — 강등 대신 반납만 쓴다
- **선택**: (b)
- **왜**: 기준 1 이 갈랐다. 불변식 6개 목록에 「접두사로 권위를 안다」는 **들어 있지 않다** — 그것은 `DESIGN.md` 「key 표기」 절의 **근거 설명**이지 불변식이 아니다. 반면 (a)와 (c)는 불변식 2(key 불변)를 직접 깨고, (a)는 *"강등은 삭제가 아니다"* 도 함께 깬다. (d)는 불변식은 안 깨지만 `F-4` 가 보여주듯 강등 대상이 실제로 10건 나오는 상황에서 그 10건을 전부 삭제하게 되어 원문 규범을 잃는다.
- **되돌릴 수 있는가**: 조건부 — INDEX 필드를 없애는 것은 언제든 가능하지만, 그 시점까지 강등된 key 가 있으면 그 강등 상태를 표현할 곳이 사라진다.
- **대가**: *"key 만 보고 차단 가능 여부를 알 수 있어야 한다"* 가 성립하지 않게 된다. `FINDINGS.md` `F-2` 에 기록했다. 이것은 설계 수정이 필요한 지점이며 이 결정으로 닫히지 않는다.

## D-7 — `|S| ≥ 2` 를 차단 방향 `정` 에만 적용한다 (파일럿 범위)

- **시점**: B1 / item-01-extract. `F-3` 을 만난 자리
- **막힌 지점**: 합성 후보 19개 중 8개가 참조 슬롯 1개뿐이라 `|S| ≥ 2` 를 못 채운다. 설계대로면 별칭이므로 원소로 강등되고 차단력을 잃는다. 그런데 **그중 5개는 작업이 아니라 차단 주장을 막는 조각**이다(방향 `역`). 강등하면 원문의 무효화 권한이 사라진다. 설계에 이 경우의 처리가 없다.
- **선택지**:
  - (a) 설계대로 8개 전부 원소로 강등한다
  - (b) 방향 `역` 조각을 다른 원소와 묶어 억지로 `|S| ≥ 2` 를 채운다
  - (c) `|S| ≥ 2` 를 방향 `정` 에만 적용하고, 방향 `역` 은 슬롯 1개도 합성으로 인정한다
  - (d) `|S| ≥ 2` 규칙 자체를 버린다
- **선택**: (c)
- **왜**: `|S| ≥ 2` 의 **근거를 보고 정했다.** 설계가 든 이유는 *"별칭에 권위를 주면 원소가 우회 경로로 차단력을 얻는다"* 다. 이 우려는 방향 `정` 에서만 성립한다 — 방향 `역` 인 단일 조각은 원소에 차단력을 **주는** 것이 아니라 **빼앗는** 것이므로 우회 경로가 생기지 않는다. 즉 (c)는 규칙을 약화시키는 것이 아니라 **규칙의 근거가 미치는 범위로 규칙을 좁히는 것**이다(기준 1). (b)는 실제로 시도했고 실패했다 — 묶을 원소를 저작해야 하고 그 조합이 원문에 없는 주장을 만든다(`F-3` 참조). (a)는 원문 규범 5건을 잃는다. (d)는 별칭 문제가 방향 `정` 에서 그대로 살아난다.
- **되돌릴 수 있는가**: 예. 방향은 INDEX 필드이므로 조건을 다시 넓히면 된다.
- **범위**: **파일럿 한정.** 이것은 설계 수정 제안이며, B2 이후에 같은 판단을 반복하지 말고 설계 자체를 고칠지가 별도로 결정돼야 한다.

## D-8 — 강등 판정 기준을 「자립하는가」에서 「복원 후에도 규범 내용이 남는가」로 좁힌다

- **시점**: B1 / item-01-extract. `F-4` 를 만난 자리
- **막힌 지점**: 설계의 강등 기준은 *"분해했을 때 각 조각이 의미를 갖지 못하면 권위 없는 원소다"* 인데, 실측하면 「의미를 갖는가」가 아니라 **「주어를 생략했는가」** 를 재고 있다. 강등 대상 10건 **전부**가 주어 생략(7) 또는 조응(3) 때문이고, 규범 내용이 없어서 강등된 것은 0건이다. 이 기준을 그대로 쓰면 저자가 주어를 채워 쓰는 것만으로 차단력을 만들 수 있다.
- **선택지**:
  - (a) 설계대로 「절단 직후 자립하는가」로 판정한다
  - (b) **「주어·조응을 복원한 뒤에도 규범 내용이 남는가」** 로 판정한다
  - (c) 판정 전에 원문을 자립적으로 다시 쓴 뒤 분해한다 (전처리)
  - (d) 강등 판정을 사람에게 남기고 기계 기준을 두지 않는다
- **선택**: (b)
- **왜**: 기준 1. (a)는 「권위 = 의미」라는 설계의 명시 원칙을 실제로는 「권위 = 문장 작성 방식」으로 바꿔 놓으므로, 설계를 따르는 것처럼 보이면서 설계의 근거를 깬다. (c)는 **원문 개정이 추출의 선행 조건**이 되어 `item-01` 의 *"원문을 고치지 마라"* 를 정면으로 위반하고, 무엇보다 상류역행(원문을 고치러 올라감)을 이 트랙 안에서 재현한다 — 트랙이 끊으려는 바로 그 기전이다. (d)는 `F-4` 를 기록만 하고 판정을 미루는 것이라 파일럿이 닫히지 않는다.
- **되돌릴 수 있는가**: 예. 판정 기준이지 산출물 구조가 아니다.
- **남는 것**: 「복원」의 범위(어디까지가 복원이고 어디부터가 저작인가)는 여전히 사람 판정이다. 이 파일럿에서는 **원문 안에 선행사가 존재하는 경우만 복원**으로 인정했다 — `RA-08` 의 "해당 primitive" 는 `RA-07A` 가 선행사이므로 복원, 선행사가 없으면 저작.
