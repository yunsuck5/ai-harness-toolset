# review Design

## Header

범용 리뷰에서 검증할 목적과 운영 조건에 맞춰 상황 카탈로그와 모델·effort 선택을 현실화한다. 용도별 선택 의미, 신규 effort 지원, 기존 응답의 위임 관측을 한 변경으로 연결한다.

지속할 선정 기준과 의미 경계는 `review_spec.md`의 목표 상태에 담고, 구체 조합 값과 용도 설명은 config가 소유한다. 이 문서는 방향·이유·소유 관계를 설명하며 구현 순서는 `review_plan.md`에서 다룬다. 문서 자체는 commit·push·global 설치 변경 승인이 아니다.

## 왜 바꾸는가

동일 값으로 출하한 기존 카탈로그에는 변경 규모·파일 종류·검토 관점·민감도가 함께 놓여 있다. 파일 수나 확장자만으로 자원을 선택하면 작은 계약 변경을 과소평가하고, 일반 문구 수정을 과대평가할 수 있다. 기획서의 논리·요구 완전성·실현 가능성, 보고서의 근거·수치, 운영 절차의 실패 대응도 범용 리뷰의 대상이다.

카탈로그의 출발점은 무엇을 검증하는가다. 모델·effort는 그 선택의 결과이며, 같은 조합을 쓰는 항목도 검증 목적과 선택 이유가 다르면 구별할 가치가 있다. 기존 상황 목록을 모델 이름과 effort 조합 목록으로 대체하지 않는다.

## 실전 근거와 적용 범위

C# 소켓 서버 프레임워크의 전체 프로젝트 정적 리뷰에서는 입력·메모리 경계, 실제 자원의 소유권, 지연 완료, 반복 검사, 종료·복구 경로에서 분석 차이가 나타났다. 결함 발견과 제안된 수리안의 타당성도 달랐다. 소유권을 깊게 추적한 분석이 전면 재작성의 비용 우월성까지 입증하는 것은 아니다.

이 관측은 전문 대안을 남기고, 논리·근거·수리 비례성·범위 검토를 구별할 근거다. 한 프로젝트의 개별 발견을 해당 국소 목적만의 비교 실험이나 비코드 리뷰 전반의 우위로 확대하지 않는다. 문구 의미 보존·일반 정량 문서·기획 완전성 등 직접 비교가 없는 목적에도 선택 후보를 제시하되, 실측과 적용 가설·품질 여유를 구별한다.

실전 검토 대상은 대상 유형으로 설명한다. 개인 프로젝트 식별자, 로컬 경로, 실행별 ID·시간·사용량·원문은 이 설계의 지속할 의미에 포함하지 않는다. 구독 사용량 환산과 실제 계정 한도 차감률은 별개의 관측이다.

## 선택 구조

검증 목적은 국소 정확성, 의미 보존, 논리, 요구 완전성, 근거, 수치, 실현 가능성, 계약, 권한·책임 경계, 교차 정합성, 절차·복구, 코드 상태·수명, 코드 데이터 경계, 검증 탐지력, 복합 종합을 구별한다. `default`는 목적·문맥의 모호함을 다루고, `highest`는 검증 목적과 별개인 명시 최고 자원 요청을 나타낸다.

통상 중요 리뷰는 효율 지점보다 한 단계 여유를 두며 최상위 모델의 xhigh를 기준으로 한다. 속도·구독 사용량·유휴시간은 별도 고려 사항이다. 낮은 모델의 높은 effort를 빠른 리뷰 또는 자동으로 저렴한 리뷰로 취급하지 않는다. 실전에서 드러난 특정 분석 능력은 전문 대안의 근거가 되지만 일반 모델 순위를 대체하는 새 고정 서열은 아니다.

명시 최고 요청에는 최상위 모델과 ultra를 적용하고, 구체 모델·effort 요청은 각 축에서 우선한다. 중요한 영향이 있는데 운영 조건만으로 자동 하향하지 않는다. 범위와 관점은 자원 선택에 따라 줄이지 않는다. 이 기준의 상세 의미와 effort별 용도는 Spec에 둔다.
기본 조합과 운영·전문 대안을 함께 전달하되 검증 목적과 자원 선택을 섞지 않는다. 대안의 구체 모델·effort와 적용 조건은 같은 config entry의 description에 보존하고, 호출자는 이를 읽어 같은 목적 category에 기존 명시 override를 적용한다. 조합을 바꾸기 위해 다른 검증 목적의 키를 빌려 쓰거나 별도 분류 구조를 만들 필요가 없다. 사용자 명시값은 대안보다 우선하며 description은 호출자를 위한 자유문 설명으로 남긴다.

## Owner surface model

| Active surface | 소유할 의미 |
|---|---|
| `config/reviewer.json` | 기본 모델·effort 값, 목적별 카탈로그와 운영·전문 대안의 구체 조합·조건을 담은 description |
| `config/reviewer.schema.json` | config/entry의 형식, description의 정보성 의미, 입력 해소·검증 계약 |
| `snippets/claude-skills/ai-harness-review/SKILL.md` | 목적·중요 영향·운영 조건에 따른 선택, 같은 category의 대안을 기존 명시 override로 적용하는 판단, 명시 최고·커스텀 요청 처리 |
| `scripts/review-run.ps1` | 단일 category lookup·축별 명시값 우선순위, effort 허용값과 실제 적용값 관측, 기존 호출 경계 |
| runner preamble·result template | 기존 Notes에서 아는 만큼 보고하는 서브에이전트 역할·모델·effort·깊이 |
| tests | config·입력 해소·적용 관측의 기능 계약 |

Spec은 선정 기준과 active owner의 의미를 대조하는 목표 명세다. 실제 선택이 Spec 열람을 요구하지 않도록 배포 표면이 자기 의미를 운반한다. 구체 모델 버전을 Spec·skill·script에 중복 고정하지 않고, schema가 config의 상황 설명을 별도로 소유하지 않게 한다.

## 호환과 관측의 경계

기존 키의 lookup과 검증 의도를 보존하면서 새 호출은 더 구체적인 목적을 고를 수 있게 한다. 키 삭제로 기존 호출을 scalar fallback에 빠뜨리지 않고, 목적별 분리를 자동 alias 변환으로 구현하지 않는다. `default` entry 선택과 category soft miss의 scalar 해소를 구별한다.

max·ultra 지원과 추천 목록은 별개다. high/xhigh 중심의 추천을 이유로 기존 낮은 effort 입력을 제거하지 않는다. 모델별 지원 실패를 조용한 모델 교체로 숨기지 않는다.

위임은 기존 Notes의 관측으로 다룬다. 실제로 모르는 값은 unknown으로 두고 부모 값의 상속을 추정하지 않는다. 별도 collector·조회 의무·위임 깊이·토큰 제한·재귀 억제 정책을 추가하지 않는다. 기존 reviewer의 읽기 전용 역할과 단일 canonical reviewer unit 계약은 유지한다.

## 통합 범위와 비목표

카탈로그·schema·선택 skill·runner의 max/ultra 지원 및 적용값 관측·Notes 안내를 함께 반영한다. 모델 지원만 먼저 완료하고 카탈로그 의미를 남기는 방식으로 분리하지 않는다.

분류 점수기, capability registry, dispatcher, 운영 조건별 키의 조합 증식, 자동 추가 reviewer, scheduler, fallback/retry, 새로운 결과 parser gate는 도입하지 않는다. canonical artifact·coverage·권한·설치 구조의 변경은 포함하지 않는다.

상황별 의미와 선택 근거를 Plan에서 처음 결정하도록 미루지 않는다. Plan은 이 방향을 구현할 표면·호환 처분·검증과 후속 의미 변경의 되돌림 지점을 정한다.
