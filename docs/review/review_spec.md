# review Spec

## Header

**이 문서는 무엇인가.** review 도메인의 **목표 상태 명세**(spec-of-record)다 — Codex review subsystem 이 무엇이고, 어떤 active surface 가 그 행동을 소유하며, 어떤 경계가 항구적으로 유지되는지를 normative 문장으로 명세한다.

**이 체인이 끝나면 무엇이 되는가.** review의 기계 계약은 scripts/templates/tests에, operator 판단 규율은 배포 skill에 간결히 놓이고, 이 spec과 `review_backlog.md`는 그 target state와 future work를 각각 기록한다.

**이 문서가 아닌 것.** 구현 절차서 아님 · operative authority 아님(behavior 는 active surface 가 소유하고 이 spec 은 명세·대조될 뿐) · 프로젝트 공용으로 채택·기각된 용어의 한 줄 의미 home 아님(`rules/terminology-glossary.md`; review-local 의미는 이 owner가 소유). 이 spec 은 mutation/commit/push 승인이 아니다(1회 진술).

## 목표 상태

**Review 의 정체.** review 는 한 작업(`/goal`) 또는 한 review gate 에 대한 **독립 reviewer 의 검토를 canonical artifact 쌍으로 닫는 quality gate** 다. canonical reviewer verdict는 `review-run.ps1`가 호출한 reviewer unit의 semantically usable result에서만 발급되며, caller self-review는 packet context와 별도 caller 판단일 뿐 reviewer verdict를 대체하지 않는다. 어떤 verdict 도 commit / push / publish / merge / release / deployment / adoption / config mutation 을 자동 승인하지 않는다 — 다음 단계는 항상 사용자의 별도 명시 결정이다. review subsystem 은 **maintenance mode** 로 운영된다: 신규 기능·reviewer adapter·multi-reviewer orchestration·review-history DB·cross-run 집계·자동 retention 은 별도 scoped 승인 없이 도입되지 않으며, bug fix 와 계약 명확화는 in-scope 다.

**Canonical artifact 모델.** 한 review 기록은 `<ProjectRoot>/log/review/<review-task-id>/<perspective>/pass-NN/` 의 **three-level layout** 으로 닫힌다. 외부 task 하나는 서로 다른 목적·gate의 독립 review campaign을 여러 개 가질 수 있고, `<review-task-id>` 는 그중 하나에 결박된 공개·purpose/gate-bound campaign key다 — 사람·machine·session·process identity나 권한 token이 아니다. 같은 campaign은 여러 perspective와 corrective/stale 후속 pass를 포함하며, 독립 평가이거나 목적·gate·Stage가 실질적으로 달라지면 새 key를 쓴다. `Purpose`는 unit 설명과 stdout 확인값일 뿐 저장된 identity나 machine-verified equality proof가 아니다. `<perspective>` 는 review 관점(예: `local-correctness` / `system-coherence`)으로 **필수**이며 operator 가 명시한다 — 자동 추론과 two-level fallback 은 없고, single path segment 안전 규칙(charset/length·`..`·separator 금지)을 따른다. `pass-NN` 은 그 perspective 안의 corrective attempt 로 **per-perspective** 로 증가하고, 각 pass 디렉터리는 **write-once** 다 — 보완은 새 pass 로만 한다. pass 당 canonical record 는 `input.md` + `result.md` **두 파일뿐**이며 sidecar(JSON·hash·외부 staging)는 계약의 일부가 아니다.

**Campaign admission과 pass allocation.** 기본 prepare 호출은 새 campaign을 claim하며 같은 `<review-task-id>` task root가 이미 있으면 pass를 만들지 않고 실패한다. `-ContinueCampaign`은 기존 campaign에 다른 perspective 또는 corrective pass를 추가한다는 operator의 공개 assertion이지 권한이나 동일성의 기계적 증명이 아니다. continuation은 기존 task root 아래 canonical `input.md`가 하나 이상 있을 때만 허용한다. anchor 없는 task root나 input 없는 pass 형태의 legacy/crash residue는 자동 채택하지 않고, pre-contract canonical record는 명시적으로 continue한 경우만 이어 쓴다. 첫 mutation 전에 project log root부터 task entry까지, continuation/write 전에는 task entry부터 선택 write parent까지의 기존 ancestry와 canonical anchor를 다시 해석해 reparse entry나 기대와 다른 directory/file shape가 하나라도 있으면 fail-closed한다. 이 static existing-entry guard는 검사 뒤 hostile actor가 path를 교체하는 mid-invocation replacement race까지 봉인하는 보안 메커니즘이 아니다. auto allocation은 perspective 아래 후보 하나만 고르며 explicit/auto 모두 최종 pass directory의 exclusive create를 선형화 지점으로 사용한다. 같은 preselected pass 좌표를 경쟁한 호출 중 claim 성공자만 `FileMode.CreateNew` 의미로 0-byte `input.md`를 만들고 두 단계가 끝난 경우에만 성공하며 loser는 nonzero이고 다른 pass로 자동 retry하지 않으며 기존 input을 덮어쓰지 않는다. explicit 호출이 한 좌표를 먼저 claim한 뒤 auto 호출이 새 scan에서 다른 좌표를 정상 선택하면 두 allocation은 모두 성공할 수 있고 이는 silent retry가 아니다. claim 뒤 중단된 pass는 occupied orphan으로 남아 자동 cleanup·rollback·재사용되지 않는다. 선택한 perspective의 `pass-99`가 이미 존재하면 그 perspective가 range exhaustion으로 stop하며 explicit lower number로 우회하거나 새 campaign key로 자동 rollover하지 않는다. lower allocation은 성공 발행 전에 `pass-99`를 재확인한다. concurrent 점유가 확인되면 nonzero로 끝내며 이미 claim한 lower pass를 occupied orphan으로 보존한다. parent·열거를 확인할 수 없으면 역시 nonzero지만 점유 원인이나 lower artifact 잔존을 단정하지 않고 자동 retry·cleanup 없이 상태 확인을 요구한다. 다른 perspective의 pass numbering은 독립적으로 계속된다.

**input.md (operator 작성).** prepare는 새 write-once pass에 빈 `input.md`를 만들고, operator-role AI가 compact template을 필요할 때 참조해 reviewer 입력 전체를 직접 작성한다 — full-template 자동 seed mode는 없다. required H2 5종(Context / Required inspection paths / Review questions / Constraints / Final verdict)의 본문은 비어 있지 않아야 하고, informational section 들이 의미를 보탠다 — `## Target files` 는 source-managed 파일만 담고, `## Validation evidence` 는 validation 실행 claim 의 근거 evidence 경로를 담으며(부적용 round 는 짧은 N/A), `## Known concerns` 는 **confirmed disclosure** 와 **open hypothesis** 두 종류를 구분하고 caller가 알고 있는 conclusion/previous-verdict pressure를 숨기지 않는다(확정 사실을 가설로 위장하지 않는다 — disclosure 회피 금지). `## Stage` 와 `## Context` 는 정확한 review stage와 artifact boundary를 함께 식별하며 planning approval과 implementation corrected-state acceptance를 한 gate로 합치지 않는다. operator가 prepare 호출에 제공하는 Stage 값은 `design`, `implementation`, `test`, `review`, `release`의 닫힌 집합이다. 더 구체적인 review stage가 없는 ordinary code change에는 operator가 `implementation`을 선택하며, 이는 script parameter default나 자동 추론이 아니다. 사용자 소유 task-grade × finding-class 표는 명시적으로 제공된 경우에만 grade/class를 review 전 Context/Constraints에 기록하고, 표가 없으면 subsystem이 default를 발명·추론하지 않는다. 활성 placeholder 는 `AI_TO_FILL_` namespace 로 한정되고 미치환 시 기계 거부된다. 정확한 heading 집합·placeholder regex·금지 문구의 값은 active surface(template + input verifier)가 소유한다.

**result.md (dual-authored).** reviewer output의 runtime 지시는 runner preamble이, shape 검증은 기존 result verifier가 소유한다. active reviewer adapter가 verdict/disclosure 본문을 작성하면 runner는 verdict와 4개 disclosure H2의 **기계적으로 완전한 candidate shape**를 먼저 확인하고 그 끝에 machine run-fact provenance 블록을 append한 뒤 같은 verifier로 final canonical shape를 다시 확인한다. 같은 invocation에서 reviewer session pointer가 관측되면 runner는 이를 H1 stdout과 provenance의 공개 `reviewer-session-id`로 함께 기록하고, 관측되지 않으면 `not-observed`로 드러낸다. 이 tail check는 새 parser gate나 provenance-content 검증이 아니다. provenance append가 실패해도 unchanged candidate의 선검증은 유효하므로 tail check가 통과하면 `review-run: PASS`·candidate H1 token·exit 0을 유지하고 `provenance-persisted: FAILED`로 실패를 드러낸다. append 성공 여부와 무관하게 tail check가 실패하면 runner는 PASS/H1 success line 없이 review result unavailable로 nonzero 종료하고 failed pass 및 이미 기록된 실제 provenance를 보존한다. reviewer 호출 실패, `result.md` 미생성, verdict 또는 required disclosure shape를 갖추지 못한 결과도 각각 invocation unavailable / review result unavailable인 실패 상태이며 reviewer verdict가 아니다. shape-valid body가 operator intake에서 내부 모순 때문에 unusable로 판정될 수 있으며, 이때 provenance는 실제 실행 사실로 남지만 body의 verdict token은 consumable reviewer verdict가 아니다. candidate verdict token은 `## Verdict` heading 1개 아래 첫 비어있지 않은 줄의 **lowercase 정확 일치** 로만 읽고, 4개 disclosure H2(Blocking findings / Non-blocking concerns / Review limitations / Assumptions relied on)는 각각 정확히 1회 존재해야 한다. named risk의 disclosure home은 `## Non-blocking concerns`이며 generic Findings/Risks bucket을 canonical skeleton이나 runtime 권고로 두지 않는다(추가 H2를 parser로 금지하지는 않는다). target artifact의 지속성이 severity나 closure에 영향을 주면 해당 finding prose에 이를 적고, transient라는 이유만으로 자동 nonblocking 처리하지 않는다. `## Counter-argument` 는 verdict에 대한 strongest case AGAINST를 적는 **optional, strongly-recommended, non-parser** pressure-test 관례다 — substance 없는 round는 짧은 literal로 두고 ceremonial boilerplate를 피한다. 정확한 shape의 값은 active surface(result template + verifier)가 소유한다.

**Verdict 어휘와 next-action.** 기계적으로 완전한 candidate body에는 정확히 한 verdict token이 있고 그 어휘는 `yes`(blocking 없음 — 후속은 사용자 결정, 자동 진행 금지), `no`(blocking 있음 — rational blocker의 처분과 필요한 corrected-state review 또는 stop/report로 이어지며 `no`만으로 batch를 닫지 않음), `yes with risk`(`yes` 의 동의어가 아니다 — `## Non-blocking concerns`의 named risk에 명시적 사용자 수용 또는 re-review 경로가 필요함) 셋뿐이다. invocation/shape-result unavailable에는 token이 0개이고, shape-valid body도 operator가 내부 모순 때문에 unusable 판정하면 consumable reviewer verdict가 0개다. 어느 경우도 네 번째 verdict가 아니다. `no`의 각 blocking finding은 ① 구체적인 failure mode/path 또는 직접적인 contract/acceptance 위반, ② 영향받는 consumer 또는 decision, ③ 실패한 function·outcome·contract를 식별해야 한다. unknown·missing information·unperformed check 자체는 그 부재가 명시적 필수 계약을 직접 위반하지 않는 한 blocker가 아니며, 이 rational basis가 없는 `no`는 semantic-unusable이다. blocking 여부의 source-of-truth 는 `## Blocking findings` 본문이며, blocking/non-blocking 경계는 review scope 와 finding substance 가 함께 결정한다. operator는 rational blocker 각각을 `in-scope correction` / `out-of-scope stop` / `reviewer overreach` / `false-positive or evidence gap` 중 하나로 처분한다. 뒤의 두 처분은 evidence-bound 설명과 명시적 사용자 결정을 요구하며 finding을 자동 기각하거나 `no`를 다른 verdict로 바꾸지 않는다. prior `no`와 finding은 후속 correction·challenge·review 뒤에도 write-once canonical history에 그대로 보존한다. 사용자 표가 있더라도 결과를 본 뒤 threshold를 낮추거나 blocking finding을 자동 비차단화하지 않는다. follow-up pass 전에는 changed reviewed artifact, newly available evidence, corrected/clarified material claim 또는 input, 또는 허용된 next action을 바꾸는 blocker-bound 명시적 사용자 disposition 중 review를 바꿀 수 있는 closure basis를 기록한다. review 횟수 상한은 없지만 reviewed state·evidence·material claim·blocker disposition이 모두 같은 재시도는 stop/report한다. operator 는 verdict line 만으로 다음 행동을 정하지 않고 4 disclosure 본문을 함께 읽는다 — shape PASS와 runner H1 token은 commit fitness 또는 consumable judgment의 자동 보증이 아니다.

**Coverage 어휘 (축 분리).** `dual-perspective coverage` 는 local correctness review + system coherence review 두 관점을 각각 독립 review unit 으로 충족하는 **coverage 정책**이다. 한 invocation 에 두 perspective 를 공유하지 않으며 canonical packaging 은 `two focused invocations` 다. 한 관점의 의도적 생략/축소는 `coverage-limited review`(caller rationale + 최종 보고 disclosure 필수), reviewable 변경 없음은 `no-reviewable-change report`(caller-side 보고, verdict 아님)다. Applicable project rule의 exact predicate를 충족한 `retirement-only closeout`은 reviewed target-state meaning을 바꾸지 않고 qualified lifecycle retirement/state transition만 수행하므로 이 no-reviewable 분류를 사용하며 canonical pass를 만들지 않는다. **invocation count · artifact pass count · corrective loop count 는 서로 다른 축**이며 한 토큰으로 합쳐 표기하지 않는다.

**Operator stance.** operator-role AI 는: ① 사용자가 지정한 uncommitted working-tree 변경과 stated base 대비 committed delta 의 전부 또는 일부(또는 호명된 subsystem 의 tracked 집합)로 intended target을 정하고 의도적 제외를 disclose 한다 ② off-repo/추가 읽기 경로를 source-of-truth 로 승격하지 않는다. Caller가 absolute existing directory/file을 runner parameter로 제공하고 input에 exact load-bearing target을 적으면 reviewer가 직접 읽는다. Input·proxy·staging·workspace copy로 본문을 우회 복제하지 않는다 ③ 승인 scope 밖 source mutation·runtime/외부/user-global 영역 mutation·설치 payload refresh·commit 류 실행이 필요해 보이면 stop/report 한다 ④ 이전 판단·작성·주장의 오류를 발견하면 무엇을/왜/현재 상태로 분리해 **retraction 보고** 한다 ⑤ source repo / runtime artifact / 외부 참고 / user-global 의 네 경계를 구분해 다룬다 ⑥ review tooling 자체를 수정하는 작업은 승인된 read-only inspection으로 이미 확인 가능한 repository status/diff/history, candidate engine payload, installation metadata, already-existing user-provided checkout을 먼저 소비해 engine 적격성을 판단한다. 글로벌 stable 설치의 current payload-head provenance는 canonical 3-way cross-binding(`payload-manifest.json.head == payload-marker.json.head == install.json.lastUpdatedHead`; 최초 설치 history 인 `install.json.installedHead` 제외)으로 확인·기록하되, 이는 metadata가 함께 지칭하는 payload head만 확립한다. 기존 사실이 대상 review-machinery 변경을 모두 배제하는 usable pre-change engine을 affirmative하게 확립할 때만 사용하고, 포함이 확인된 in-development engine은 부적격이다. 적격성만 다시 증명하려고 새 checkout을 만들거나 hash·preimage·byte/content binding·comparison artifact·evidence bundle을 생성·지속하지 않는다. existing facts가 missing/unreadable/mismatch 또는 그 밖의 이유로 충분하지 않으면 in-development runner로 fallback하지 않고 engine-eligibility gap을 stop/report한다 ⑦ failed 또는 semantic-unusable unit 뒤에는 corrected invocation/input과 closure basis를 먼저 제시하고 명시적 scoped user approval을 기다린 뒤 새 pass를 발급·실행한다; reviewed state·evidence·material claim·blocker disposition이 모두 같으면 새 pass를 만들지 않고 stop/report한다. `review-run` 시작 뒤 `input.md`나 기존/failed pass를 고치지 않고 새 canonical pass directory 밖 mutation이 필요하면 stop/report 하며, reviewer CLI 부재는 install/refresh 없이 환경 결손으로 보고한다 ⑧ canary-first 는 실제로 사용 중인 engine pipeline 의 new/changed template·contract·perspective·artifact-binding 에만 적용한다 ⑨ canonical review 호출의 caller timeout은 7일로 두고, 사용자의 지시 없이는 진행 중인 호출을 취소하지 않는다.

**Reviewer 경계.** reviewer 는 read-only 또는 동등 guard 아래에서 판단만 한다. Declared target·required paths·relevant repository context를 가용한 read-only 도구로 직접 확인하며, Git delta면 live status와 applicable working-tree/stated-base diff를 포함한다. 이름·경로·식별자·구조 변경에서는 filename/path·bare token/ID·folder-as-bucket·semantic phrasing 네 class의 잔여 참조를 read-only로 확인하고, 삭제 변경은 case-insensitive 검색·철자/대소문자 변형·bare-section 참조까지 포함한다. review 중 어떤 표면도 mutate/fix하지 않고 packet 결함을 silent repair하거나 intended target을 재정의하지 않으며, 가용한 material read-only check를 생략하고 limitation으로 대체하지 않는다. caller packet이 explicit required contract를 위반하면 그 acceptance breach를 blocker로 지목해 `no`를 발행한다. reviewer capability gap이 비-material이면 limitation을 공개하고 정상 verdict를 발행하며, required inspection 또는 target completeness에 material이면 acceptance breach를 blocker로 지목해 `no`를 발행한다. `yes with risk`는 확인하지 못한 check의 대체 토큰이 아니다. `no` blocker는 구체적인 failure mode/path 또는 직접적인 contract/acceptance 위반과 영향받는 consumer/decision, 실패한 function/outcome/contract를 연결하며, 명시적 필수 계약의 부재가 아닌 unknown·missing·unperformed check 자체만으로 발행하지 않는다. target의 broad validation/build/test 재실행은 **opt-in** 이다 — review input이 exact command·작업 디렉터리·read/write 기대·허용 산출 경로·의존 가정·timeout·해석 경계·sandbox 한계 보고 방식을 명시해 authorize 한 경우에만 하고, 그렇지 않으면 evidence를 inspect하고 비재현 사실을 limitation으로 보고한다. 비재현은 자동으로 target risk가 아니다 — 승격에는 독립 근거(누락/stale evidence·scope mismatch·정적 모순·명시적 고위험 공백)가 필요하다.

**Validation evidence (형식 규약).** evidence 는 `<ProjectRoot>/log/evidence/<scope>/<case>/validation-evidence.md` 에 남기는 **reviewer-readable single-Markdown runtime supporting material** 이고, input 의 `## Validation evidence` 는 이 bundle 을 가리킨다. evidence 는 command 재실행이 아니고, deterministic truth oracle 이 아니며, freshness binding 이 아니고, source-of-truth 로 승격되지 않는다 — canonical review record 의 input/output/sidecar 도 아니다. Tool-native raw report가 `Required inspection paths`로 제공되면 reviewer는 원본과 caller가 명시한 claim을 직접 확인하며, report 범위를 넘는 상태·권위를 별도 근거 없이 만들지 않는다. 접근 실패·부재 branch는 limitation으로 남기고 load-bearing 접근 실패의 처분은 Reviewer 경계의 3-verdict 기준을 따른다. 작성은 자발 관례이고 본문 정직성은 operator 책임이며 어떤 script gate 도 이를 강제하지 않는다. **operator-side validation scope 는 change class 에 비례한다**: script/runtime·parser gate·test code·install 경로 변경은 full suite 가 기대되고, docs/wording/formatting 류는 targeted 검증으로 충분하다 — 기대 validation 을 하향하면 change class·수행/미수행·사유·잔여 위험을 분리해 보고한다(미수행 자체는 결함이 아니고 정직 disclosure 가 요건이다). validation scope 용어의 정의 home 은 `tests/README.md` 다.

**Staleness.** pass 작성 후 그 review 가 묶인 **source-managed artifact set** 이 달라지거나 reviewed artifact 의 source-managed bytes/content·path·Git mode·target-relevant meaning 이 바뀌면 그 pass 는 stale 이고, 같은 campaign key·perspective 아래 `-ContinueCampaign`으로 새 pass 를 배정해 재검토한다. `retirement-only closeout`의 자격과 exact transaction shape는 applicable project lifecycle rule이 소유한다. Operator는 proposed closeout transaction의 전체 source delta가 그 predicate와 정확히 일치하는지만 판정한다. Predicate가 성립한 closeout은 reviewed target-state meaning을 바꾸지 않고 qualified lifecycle retirement/state transition만 수행하므로 pass를 stale하게 만들지 않고 새 review target도 만들지 않는다. Predicate가 없거나 적용할 수 없거나 review-bound artifact set·source-managed bytes/content·path·Git mode·target-relevant meaning의 추가 변경이 하나라도 있으면 ordinary change로 candidate 단계에 되돌려 stale/corrected-state review를 적용하며, closeout pass로 그 불일치를 정당화하지 않는다. operator 가 호출 전에 알았던 concern 을 disclose 하지 않았음이 사후 발견되면 그 verdict 는 **stale-by-omission** 으로 후속 결정의 근거가 될 수 없다. stale 판단은 operator 와 사용자 책임이며 기계 검출은 도입하지 않는다.

**Script 책임 (deterministic gate only).** review scripts 는 의미 판단을 하지 않는다. 기계 책임은: campaign new/continue admission과 canonical anchor 확인 · project log root/task/anchor/selected write ancestry의 static reparse·shape fail-closed · pass 경로의 review-root + task-root containment 검증 · auto/explicit 단일 후보의 exclusive directory claim과 no-clobber 빈 input 발급 · lower allocation 뒤 selected perspective `pass-99` terminal 재확인 · input 의 required H2/본문/placeholder 기계 gate · reviewer preamble과 `input.md`를 caller가 조립한 strict UTF-8 no-BOM byte sequence 그대로 stdin에 전달 · 한 `(perspective, pass)` review unit당 reviewer CLI 정확히 1회 실행 · 동일 invocation의 공개 reviewer session pointer 관측 · invocation 성공과 result 존재·candidate shape 선검증 · provenance append 시도 뒤 final canonical shape 재검증 · 종료 코드 전달 — 이것뿐이다. scripts 는 campaign purpose의 실질 동일성, hostile mid-invocation path replacement, finding 의 의미·재검토 필요·후속 단계를 판단하지 않고, 같은 preselected 좌표 collision을 다른 pass로 자동 retry하거나 orphan을 cleanup하지 않으며, verdict 를 읽어 어떤 것도 자동 트리거하지 않고 본문을 sidecar 파일로 분산하지 않는다. runner 는 final shape가 성공한 경우에만 단일 invocation 의 H1 run-facts를 stdout 으로 emit 하고 동일 실행 사실을 provenance 블록으로 result 에 append 한다. H1 token은 operator semantic intake 전에 consumable reviewer verdict가 아니다.

**Config (전부 config-driven).** reviewer model 과 effort 는 config 가 source-of-truth 다. model 은 내장 default/fallback 없이 결손 시 **fail-fast** 하고, 구체 model version 은 외부 lifecycle 에 종속되므로 config 한 곳 외의 durable 표면에 적지 않는다. explicit/category/config 어느 source에서 resolve되든 model은 machine run-fact와 provenance의 단일행 값이므로 CR/LF를 포함하면 reviewer 호출 전에 fail-fast 한다. effort 의 유일한 내장 default 는 safe default(`xhigh`)다. `categoryPolicy` 는 **분류 = operator 명시 선택(judgment), 매핑 = config 기계 lookup, 적용 = runner** 의 분리를 따른다 — 자동 추론(변경 파일/Stage/LLM 기반)은 없다. `-EffortCategory` 입력은 machine run-fact와 provenance의 단일행 값이므로 CR/LF를 포함하면 reviewer 호출 전에 fail-fast 한다. 공급되었으나 부재한 key 는 soft miss(스칼라 fallback)이고, 존재하는 entry 의 결함은 fail-fast 다. 출하 key set 은 범용 변경 class 로 generic 하고 모든 entry 가 safe floor 로 출하된다 — floor 아래 값 튜닝은 운용 데이터 후의 별도 결정이다. per-key 의미·강제 상태의 기술 home 은 config schema 다.

**Reviewer-safe invocation (구조적).** reviewer 호출의 안전은 global user config 에 의존하지 않는다 — runner 가 매 호출에 승인 없음·user-config 무시·통제된 output channel 과 read-only posture를 명시하고, 결과 기록은 runner 가 통제한다(model 의 source-tree write 가 아니다). External path가 없으면 기존 read-only transport를, 있으면 broad read를 허용하되 write를 허용하지 않는 adapter-local transport를 사용한다. Broad read는 caller-declared path만 읽었다는 confinement나 실제 접근 성공의 증명이 아니다. 이 보장은 **시험된 write vector 에 한정**되며 blanket guarantee 가 아니다 — 미시험 vector·타 플랫폼·도구 버전 변경은 한계로 남고, reviewer tool 교체 시 effort/model override·output shape·safety override 는 재도출 대상이다.

**보고 계층(H1/H2/H3).** 단일 invocation 이 deterministic 하게 관측한 사실은 **H1**(runner stdout run-fact + provenance), 여러 pass 를 가로지르는 집계와 caller 판단은 **H2**(operator 최종 보고), schema 정의는 **H3**다. H2는 정상 H1을 장문 복제하지 않고 coverage·invocation/pass/corrective 축·usable verdict와 disclosure/risk/stale·validation scope·git/authority 경계를 보고한다. review-subsystem self-modification에서는 stable engine identity, reviewer-safe posture와 이상 상태를 명시한다. 없는 artifact나 verdict를 발명하지 않는다.

**Retention.** 기록의 보존 단위는 campaign task 디렉터리 또는 개별 pass 디렉터리이고, 삭제는 사용자의 수동 결정이다 — auto-prune/rotate/expire 는 없다. 실패한 pass와 exclusive claim 뒤 중단된 orphan, 확인된 concurrent `pass-99` 점유로 막힌 lower pass도 디스크에 occupied 상태로 남긴다. post-check 자체가 unavailable이면 lower artifact의 잔존을 보장하지 않고 수동 상태 확인 전 자동 retry·cleanup하지 않는다. anchored campaign의 pass orphan은 후속 auto allocation에서 소비된 번호로 취급하지만 anchor 없는 task root는 continuation하지 않는다. orphan을 자동 cleanup·rollback·재사용하지 않는다. 한 perspective의 pass range exhaustion을 explicit lower number나 새 campaign key로 자동 rollover하지 않으며 다른 perspective의 독립 numbering은 영향을 받지 않는다.

## Durable boundary

- **발행 가능한 verdict 어휘는 `yes` / `no` / `yes with risk` 셋으로 불변이다.** 기계적으로 완전한 candidate는 정확히 1개 token을 가지며, 사용 가능한 judgment는 operator intake 뒤 그 token을 정확히 1개 소비한다. invocation/result unavailable 또는 semantic-unusable candidate는 consumable verdict 0개다. 새 token·inline 형태·대소문자 변형·네 번째 verdict는 도입하지 않는다.
- **canonical layout 과 2-file 규약은 불변이다** — three-level·public purpose/gate-bound campaign key·per-perspective pass·write-once·pass 당 input/result 두 파일. sidecar JSON·hash binding·외부 staging·machine-readable verdict 사본·flat run-id layout·hidden person/machine/session identity 는 도입하지 않는다. 동일 invocation에서 관측해 `result.md` provenance에 공개한 purpose-bound reviewer session pointer는 수동 trace-back용 정보성 metadata이며, campaign key·권한·verdict·자동 후속 trigger가 아니다.
- **parser gate 는 확대하지 않는다.** 현행 기계 gate(입력 5-H2·verdict shape·4 disclosure H2 count) 너머의 semantic adequacy/concern completeness/evidence sufficiency lint·sub-shape lint·자동 검증은 도입하지 않는다 — semantic 판단은 reviewer/operator judgment 로 남는다(기계화 금지). 재개는 unsound verdict 를 유발한 구체 증거에 한정된다.
- **자동화 금지 경계**: review history 집계·DB·dashboard·multi-reviewer orchestration·fallback model 자동 사용·retry/auto-fix loop·verdict 로 후속 단계를 트리거하는 wrapper·CI 통합·daemon/watcher/scheduler·자동 retention·stale 자동 검출·evidence freshness/hash/mtime binding·deterministic validation runner 는 도입하지 않는다.
- **effort ⟂ coverage.** effort 는 coverage·evidence·packet 품질의 대체물이 아니다 — 낮은 effort 가 좁은 coverage 를 정당화하지 않고, 높은 effort 가 부실한 packet 을 보상하지 못한다. safe default 에서의 downgrade 는 명확히 단순한 local correctness packet 에 한정되며, review subsystem 자체의 변경·contract 의미·cross-subsystem 경계·보안/권한 민감 변경은 downgrade 하지 않는다.
- **model 비고정.** 구체 reviewer model version 을 scripts/docs/templates 의 durable 기본값으로 박지 않는다 — config 가 유일한 source-of-truth 이고 결손은 fail-fast 다.
- **evidence 는 승격되지 않는다** — runtime artifact 이며 commit/push 대상이 아니고 truth oracle 이 아니다. source 트리에 evidence 파일을 두지 않는다.
- **review 는 Brief 와 비경계다.** Brief 는 review 의 input 도 output 도 아니고, brief shape 검사의 PASS/FAIL 은 verdict 가 아니다.
- **rejected umbrella 의 부활 금지** — evidence/global-invocation/instruction-surface 를 독립 도메인·시스템·공유 계약으로 되살리지 않는다(glossary 의 rejected 분류 유지).
- **`.gitignore` 자동 변경 금지** · target project 의 instruction file/global filesystem 자동 변경 금지 · `log/` 는 release/snapshot 에 포함하지 않는다.
- **idea-only 항목의 승격 경계**: backlog 의 idea-only 행(adversarial pre-pass·multi-reviewer 류)은 implementation 후보가 아니며, reopen 조건 충족 + 사용자 별도 결정 + 별도 scoped goal 없이 구현으로 진입하지 않는다. Counter-argument 의 parser 강제(과거 Option A)는 비도입 결정이 유지된다.

## Cross-domain interface

- **install-update (footprint 경계)**: `<ProjectRoot>/log/` 는 target project 의 유일한 persistent footprint 이고 `log/review/`·`log/evidence/` 는 그 아래 runtime 트리다 — gitignored 성격과 channel 구조의 owner 는 install-update 도메인(`INSTALL.md`)이며, 이 spec 은 그 경로 interface 만 의존한다. 타 도메인의 `log/evidence/**` 사용(기록처 지정)은 이 경로 interface 사용이고 evidence 형식 의미에 대한 의존이 아니다.
- **ToolRoot 해석**: review scripts 는 resolved `<ToolRoot>` 의 scripts/config 를 사용하고 operator는 필요할 때 그 ToolRoot의 input/result template을 작성 reference로 읽는다 — channel 해석 순서의 owner 는 install-update/global-invocation 표면이고 이 spec 은 그 결과 경로만 의존한다.
- **terminology**: 프로젝트 공용으로 채택·기각된 용어의 한 줄 의미는 `rules/terminology-glossary.md` 가 single home 이다 — 이 spec 은 그 의미를 일관 사용할 뿐 재정의하지 않는다. coverage 5축 등 review 도메인 고유 운용 어휘의 상세 의미는 이 spec 이 소유한다(`review owner surface`).
- **글로벌 배포 티어**: 배포되는 review 표면(skill·templates·scripts·config)은 review 의미를 **self-contained** 로 운반한다 — 동작의 완성이 repo 의 review 도메인 문서 읽기에 의존하지 않으며, **review 도메인 문서로의 경로 참조를 갖지 않는다.** (비-review 문서로의 비-behavior 주석 참조 — 예: PowerShell 정책 주석 — 는 그 문서를 소유한 도메인의 경계이며 이 spec 의 대상이 아니다.) review 의미의 home 은 이 spec 과 그 active surface 들뿐이다.
- **brief**: 위 Durable boundary 의 비경계 진술 외에 brief 도메인의 semantics 를 참조하지 않는다.
